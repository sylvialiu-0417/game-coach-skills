# 已有知识库的接入与教练能力补强

## 第一步 盘点已有能力

对现有库做样本检查，不预设要迁移或重建。登记存储形式、条目类型、来源与许可、更新时间、版本字段、可用检索接口、元数据过滤、引用返回、ACL、延迟和已有评测。抽取真实问题及失败轨迹；保留原文和当前回答，避免只看库的目录就判断覆盖率。

最低交付物是 `kb_inventory`：库的访问方式、可检索范围、来源可信度、版本粒度、已知缺口和服务负责人。若库不能按游戏和规则版本过滤，不应直接接到多游戏教练的玩家入口。

## 第二步 做字段映射与能力矩阵

把现有条目映射到通用字段：`game_id`、`mode_id`、`ruleset_id`、`entity_refs`、`knowledge_type`、`source_ref`、`status`、`valid_from/to`、`applicability`。映射可在检索适配器完成，不强求改变原库结构。无法确认来源、版本或适用范围的条目进入待核对集，不按已发布事实使用。

按教练任务列“能答 / 条件可答 / 不能答”：规则解释、养成或战术建议、实时提示、赛后复盘。每格写明知识证据、所需状态字段、可观察性、工具接口和最大延迟。例如库有团队策略条目但没有队友位置/技能状态接口，只能解释策略条件，不能下确定的当局指令。

## 第三步 找出真正瓶颈

用带标注的问题回放现有系统，逐例分类：

- **知识缺口**：库里没有可靠且当前版本有效的条目 → 补来源和条目。
- **检索漏召**：库里有，但过滤、别名、切块或排序没找到 → 改检索及元数据，不盲目加新文档。
- **证据冲突**：版本、模式、来源不一致 → 完善优先级和冲突处理。
- **状态缺失**：策略需要当前信息，但宿主没提供 → 补状态接口或收窄能力。
- **决策错误**：证据和状态都有，Agent 仍给出不适用建议 → 改 Skill、模型或校验器。
- **交互错误**：建议正确但太迟、重复或打断玩家 → 调教练触发与展示策略。

## 第四步 小范围接入并扩展

先选一个可验证的教练任务，建立基线样本、当前库映射和游戏适配器，接入只读检索，跑离线评测；再接状态工具和主动提示。每扩大一个游戏、模式或教练能力，都要提供对应的适配配置、独立样本和上线门槛。不得用一个游戏通过证明全部游戏可用。

接入完成应产生四件可审查产物：`kb_inventory`、字段映射、能力矩阵、评测基线。模板字段见 [调用契约](contracts.md)；两个虚构游戏示例见 `examples/`。
